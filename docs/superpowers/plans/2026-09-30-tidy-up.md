## Task 1: People and recording fixes

Three items in `people/` and `absence/services/bookings.py`.

**1a. Leaver audit note truncated before its "not cancelled" list** (`people/services/employments.py:_cancel_after`). The note is cut to 200 characters (`AuditEntry.note` is `max_length=200`) after joining, and the "not cancelled" part comes last, so with several cancelled absences the part HR most needs is lost. Change `_cancel_after` so the note reads, in this order: the not-cancelled list first (`not cancelled: <absence> (<reason>); ...`), then the cancelled part as a count followed by the list (`cancelled 3 absence(s) after the leaving date: ...`). If the joined text still exceeds 200 characters, cut it to 199 characters and end with `…` so the truncation is visible. Tests: a leaver with enough live absences that the old order would have lost the "not cancelled" part (make one uncancellable by closing its pot's year with `year_end.close`, or by any existing means the tests already use for a closed pot) — assert the note starts with `not cancelled:` and is at most 200 characters; and a note with nothing left over is unchanged in meaning.

**1b. Recorded sickness carries no "Recorded by" comment** (`absence/services/bookings.py:record`). When `record` is called with an empty `comment`, approve with `Recorded by <name>` where `<name>` is the actor's employee name (`people.services.access.employee_for(actor).name`) or, with no employee record, the actor's email. A comment the caller gives is kept as it is. Tests: `record` with no comment sets `decision_comment == "Recorded by Jo Bloggs"`; with a comment, that comment; an actor with no Employee falls back to the email.

**1c. `Employee.work_email` help text is wrong** (`people/models/employee.py`). It says "the account's own email is what the rota receives". The API (`api/views.py`, `/api/v1/people`) sends the work email and the rota matches on `id`. Replace the help text with: `The practice email address, unique whatever its case. It is the address the rota receives for this person. Sign-in does not read it: the User field below is what links this record to a login account.` A `help_text` change needs a migration (`people/migrations/00NN_...`, `AlterField`); generate it with `makemigrations` and check `makemigrations --check` is clean afterwards. Test: `tests/test_api.py` already asserts the work email is sent; add an assertion in an existing model test file that the help text contains "the rota receives" and not "account's own email".

Docs: `docs/admin/people.md` — where the leaving process is described, one sentence that the audit note lists absences that could not be cancelled first. `docs/admin/absence.md` — where recording for someone is described, one sentence that a recorded absence carries "Recorded by <name>" as its decision comment unless a comment was given.

## Task 2: Policy year lock, bank-holiday opt-out, bank-holiday seeds

Three items around `absence/admin_forms.py`, `absence/services/bank_holidays.py`, `absence/services/nightly.py` and migrations.

**2a. A backdated policy add bypasses the leave-year lock** (`absence/admin_forms.py:PolicyForm._check_year_unchanged`). The lock only fires when an existing policy's year fields change. Adding a new policy for a contract type + absence type that already has pots, with a different leave year, backdated into a year those pots cover, double-counts days exactly as the locked edit would. Replace `_check_year_unchanged` with `_check_year`, run on add and on any edit that changes `YEAR_FIELDS` or `effective_from`, only when `Pot` rows exist for the pair (same query as now). It refuses (the existing `YEAR_LOCKED` message, or a second constant `YEAR_ADD_LOCKED` with wording that names the rule) when either:
  - another policy of the same contract type and absence type (not this instance) is active on `effective_from` and its `(leave_year_basis, year_start_month, year_start_day)` differ from this one's; or
  - the policy of that pair active on the day before `effective_from` has different year fields and this policy is not starting on the first day of its own leave year: for `Basis.FIXED` that means `effective_from.month/day != year_start_month/day`; for `Basis.ANNIVERSARY` (either side) the change is refused outright, since there is no single first day.
  The documented procedure (end the April policy on 31 December, add a January policy effective 1 January) must still pass. Tests in `tests/test_admin_policies.py` (or wherever `YEAR_LOCKED` is tested now): the documented procedure passes; a backdated add with a January year while the April policy is still active is refused; an add starting mid-year after the old one was ended is refused; an add with the same year fields backdated is allowed; an anniversary-basis change with pots is refused; a pair with no pots is free.

**2b. HR's cancellation of an automatic bank holiday is re-created nightly** (`absence/services/bank_holidays.py:_sync`). `existing` only reads APPROVED auto rows, so a row HR cancelled (they decided not to charge that day) comes back on the next sync. Add `cancel_reason = CharField(max_length=60, blank=True, default="")` to `Absence` (migration `absence/migrations/0015_absence_cancel_reason.py`), and a `reason=""` keyword on `bookings.cancel(actor, absence, reason="")` that stores it. `_sync` cancels with the constant `bank_holidays.NOT_IMPLIED = "no longer implied by the pattern or policy"`. In `_sync`, also load the CANCELLED auto rows of the window; a wanted day that has a cancelled auto row whose `cancel_reason != NOT_IMPLIED` is an opt-out: it is skipped, not re-created, and counted in a new `"kept_cancelled"` key of the returned dict (add it to the nightly's summing and result dict as `bank_holiday_kept_cancelled`). A day whose only cancelled row carries `NOT_IMPLIED` is re-created as now when wanted again. `AbsenceAdmin` shows `cancel_reason` read-only where the cancellation fields are shown. Tests in the bank-holidays test file: HR cancels an auto row, sync runs again, no new row, count is 1; the sync's own cancellation (pattern changed to no units) then pattern restored → re-created; `cancel(..., reason=...)` stores the reason; `record`/other callers unchanged.

**2c. Bank-holiday seeds end in 2028.** Add `absence/migrations/0016_seed_bank_holidays_2029_2030.py` that `get_or_create`s (by `date`, `nation="EW"`) the England and Wales bank holidays for 2029 and 2030, following `0006_seed_bank_holidays.py`'s shape, with a no-op reverse:
  - 2029: 1 Jan New Year's Day; 30 Mar Good Friday; 2 Apr Easter Monday; 7 May Early May bank holiday; 28 May Spring bank holiday; 27 Aug Summer bank holiday; 25 Dec Christmas Day; 26 Dec Boxing Day.
  - 2030: 1 Jan New Year's Day; 19 Apr Good Friday; 22 Apr Easter Monday; 6 May Early May bank holiday; 27 May Spring bank holiday; 26 Aug Summer bank holiday; 25 Dec Christmas Day; 26 Dec Boxing Day.
  And make running out visible: `nightly.run` adds the key `bank_holidays_seeded_to` (the latest EW `BankHoliday.date`, or None) to its result and logs a warning (`log.warning`) when that date is less than 400 days after today or there is none, saying to add the next year's bank holidays in the admin. Test: a migration test that the 2029/2030 rows exist after migrating (the seeded fixture in `tests/conftest.py` may cover seeds; follow how `0006` is tested), plus nightly tests for the key and the warning (use `caplog`; set the latest bank holiday relative to `localdate()`).

Docs: `docs/admin/absence.md` — bank holidays section: the seeds run to the end of 2030, the nightly log warns when they are within about a year of running out, add the next year's from gov.uk in Absence › Bank holidays; and one sentence that cancelling an automatic bank-holiday row (HR) stands: the nightly will not re-create it, and the way to charge it again is to record the day. Policies section: the add-page rule from 2a in one sentence.

## Task 3: TOIL and year-end fixes

Three items in `absence/services/toil.py`, `absence/services/year_end.py`, `absence/models/types.py`, `absence/models/policy.py`, `absence/admin.py`.

**3a. A 0-day expiry is read inconsistently.** `toil.check` treats `earned_expires_after_days == 0` as "today only" (`is not None`), `year_end._toil_lots` as never (`if days`), and `year_end.expire_carry_in` treats `carry_over_expires_after_days == 0` as never (`if not days`). Rule: blank means never, and 0 is not a value. `AbsenceType.clean` refuses `earned_expires_after_days == 0` and `Policy.clean` refuses `carry_over_expires_after_days == 0`, each with "Leave blank for no expiry; 0 would expire it the day it was earned." The services read `None` as never and any positive number as days (`is None` / `is not None` checks in all three places), so the three agree. Tests: the two clean refusals; `_toil_lots` deadline None only for None; `expire_carry_in` with None returns None.

**3b. A leaver's late TOIL claim opens a pot after they left** (`absence/services/toil.py:_pot_day`). When the day worked is in a leave year that has ended, `_pot_day` returns `today`, and for someone whose employment has ended that opens a pot for a year they are not employed in (or fails on the contract lookup). Rule: the fallback day is `min(today, employment.end_date)` when `end_date` is set. If that pot is closed, `earn`'s existing `check_open` refuses and `approve` surfaces that ValidationError to the decide page as now. Tests: a leaver (employment ended last month) claims a day in the previous leave year and the approver approves: the earned line lands on the pot containing their last day, and no pot exists with `year_start` after `end_date`; a current employee is unchanged.

**3c. No admin list of decided TOIL claims.** Register `ToilClaim` in `absence/admin.py` as `ToilClaimAdmin(ModelAdmin)`: read-only (no add, change or delete permissions; `has_change_permission` False so the change page is a view page), `list_display` = employment, day, units, status, requested_by, decided_by, decided_at; `list_filter` = status, day; `search_fields` on the employee's first and last name; `date_hierarchy = "day"`; `readonly_fields` covering every field. Tests in `tests/test_admin.py` (or the file that tests other admin registrations): the changelist loads for an HR admin with a decided claim listed, and the add URL returns 403.

Docs: `docs/admin/absence.md` TOIL section — one sentence for each: 0 is not accepted as an expiry; a leaver's late claim lands on the pot of their last day; Absence › TOIL claims lists every claim, decided ones included, read-only (decisions are made on the decide page).

## Task 4: My absences and API throttling

**4a. A still-requested absence from a previous leave year is missing from My absences** (`absence/views/requests.py:mine`). `in_view` needs `end_date >= year_start`, and "upcoming" needs `end_date >= today`, so a request made last year that nobody decided and that is now in the past appears nowhere, though it is still waiting and the employee may cancel it. Rule: a REQUESTED absence is always shown (in "coming up" if `end_date >= today`, otherwise in "earlier"), whatever its dates. Test in `tests/test_absence_views.py` (or the file holding `mine` tests): a requested absence dated before the current leave year appears under earlier with its cancel control; a declined one from that year still does not.

**4b. No throttling on the API** (`api/auth.py`). Add a fixed-window limit per client address, counted before the token check so guesses are throttled too: setting `API_RATE_LIMIT_PER_MINUTE = int(os.environ.get("API_RATE_LIMIT_PER_MINUTE", "120"))` in `config/settings.py`, the client address from `accounts.client_ip.client_ip(request)`, the counter in Django's cache (`django.core.cache.cache`, key `api-rate:<address>:<minute>`, `cache.add` then `cache.incr`, 60-second timeout). Over the limit: `429 {"error": "too many requests"}` with `Retry-After: <seconds to the end of the window>` and the usual `Cache-Control: no-store`; log a warning once per window (not per request). Declare `CACHES` explicitly in settings as `LocMemCache` with a comment that the count is per gunicorn worker, so the effective limit is the setting times the worker count, which is fine for a limit that only exists to slow a guessing client; `0` disables the limit. Tests in `tests/test_api.py`: over the limit gives 429 with `Retry-After` and no-store; the count includes unauthorised requests; a second address is counted separately; `0` disables. Clear the cache in a fixture so tests do not bleed (`cache.clear()`), and use `override_settings(API_RATE_LIMIT_PER_MINUTE=3)` rather than sending 120 requests.

Docs: `docs/admin/api.md` — the limit, the setting, the 429 shape; `docs/admin/absence.md` My absences description — a request still waiting is always listed. `deploy/` env example if one lists environment variables: add the new one.
